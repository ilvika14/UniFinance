> Based on full code review of all pipeline files:

> `src/deepguard/aasist/train.py`, `training/aasist/dataset.py`,

## ⚠️ CRITICAL: 45% EER ≈ Random Chance

An EER of 45–50% means the model is performing **no better than a coin flip**.  
This is almost always caused by **representational collapse**, **inverted class weights**,  
or a **label bug** — not by insufficient epochs or small data.

---

## 🔴 CONFIRMED Bug #1 — Master Node Not Batch-Expanded (FIXED in model but may be stale checkpoint)

**File:** [`src/deepguard/aasist/model/aasist.py` L438–L465](file:///c:/Users/HP/Desktop/deepfake(complete)/src/deepguard/aasist/model/aasist.py#L438-L465)

**What happens:**  
The `self.master1` and `self.master2` parameters have shape `(1, 1, 64)`.  
In the original AASIST implementation, these were expanded to `(B, 1, 64)` but then  
the **unexpanded** `self.master1`/`self.master2` were passed into `HtrgGAT_layer_ST11`  
and `HtrgGAT_layer_ST21`. This meant **every sample in the batch shared the same master  
representation**, making the logits nearly identical for all samples → EER = 0.5.

**Evidence in code (the fix comment says it all):**
```python
# Bug fix (Bug 3): the original code expanded self.master1/master2 into
# local variables on lines 428-429 but then immediately discarded them by
# passing self.master1/self.master2 (shape 1,1,64) to HtrgGAT_layer_ST11
# and ST21. In eval mode this makes every sample in the batch share the
# same master representation -> all logits are identical -> EER = 0.5.
```

**Impact:** EER locked at exactly **0.5 (50%)** regardless of training.  

**Risk:** If you have a checkpoint trained **before** this fix was applied, loading  
it into the fixed model may still give bad results because the weights were learned  
under the broken forward pass. You must **retrain from scratch** after fixing.

## 🔴 CONFIRMED Bug #2 — Inverted Class Weights (TWO conflicting definitions)

**Files:**  
- [`training/aasist/train.py` L248](file:///c:/Users/HP/Desktop/deepfake(complete)/training/aasist/train.py#L248): `class_weights = torch.FloatTensor([0.9, 0.1])`  
- [`src/deepguard/aasist/train.py` L255](file:///c:/Users/HP/Desktop/deepfake(complete)/src/deepguard/aasist/train.py#L255): `weights = [4.35, 0.56]` (corrected)

**What happens:**  
In `training/aasist/train.py`, the **fixed** weights `[0.9, 0.1]` for `[real=0, fake=1]`  
heavily DOWN-weight the fake class. The comment in the file even acknowledges this is  
the "Official AASIST" mapping, but your dataset convention is **opposite to ASVspoof**:

- ASVspoof official: `bonafide=1` (minority), `spoof=0` (majority)  
  → weights `[0.1, 0.9]` up-weights bonafide (class 1)
- Your project: `real=0` (minority in ASVspoof), `fake=1` (majority)  
  → correct weights should be `[0.9, 0.1]` to up-weight real... **BUT only if real really is the minority**

**The actual risk:** If your local `data/real` and `data/fake` folders are roughly balanced  
(equal files), then `[0.9, 0.1]` severely down-weights the fake class by **9×**, causing  
the model to almost always predict "real" → very high FNR → EER ≈ 0.5.

**Additionally:** the two training scripts (`src/deepguard/aasist/train.py` vs  
`training/aasist/train.py`) use **different class weight logic**, so depending on which  
script you run, you get different behavior with no warning.

## 🔴 CONFIRMED Bug #3 — Two Separate `config.py` Files With Different Settings

**Files:**  
- [`src/deepguard/aasist/config.py`](file:///c:/Users/HP/Desktop/deepfake(complete)/src/deepguard/aasist/config.py) — has `TRAIN["use_swa"] = True`, `CLASS_WEIGHTS = None`  
- [`training/aasist/config.py`](file:///c:/Users/HP/Desktop/deepfake(complete)/training/aasist/config.py) — has `TRAIN["use_swa"] = True`, `swa_start=0`, `swa_freq=1`

**What happens:**  
The two configs diverge silently. The `training/aasist/train.py` imports from  
`training/aasist/config.py`, but the model is imported from `src/deepguard/aasist/`.  
This creates a **config/model mismatch** where:
- SWA is enabled but `torchcontrib` may not be installed → silently disabled
- `swa_start=0` in the training config means SWA starts immediately, which  
  can degrade early training because the averaged model is a mix of untrained weights

## 🟠 HIGH RISK — SWA Applied After Every Best Model (Non-Standard)

**File:** [`training/aasist/train.py` L292](file:///c:/Users/HP/Desktop/deepfake(complete)/training/aasist/train.py#L292), [`src/deepguard/aasist/train.py` L424](file:///c:/Users/HP/Desktop/deepfake(complete)/src/deepguard/aasist/train.py#L424)

**What happens:**  
The official AASIST paper applies SWA **starting from epoch 60**, averaging every 5 epochs.  
Your implementation applies `optimizer.update_swa()` **every time a new best model is found**  
(which may be epoch 1, 2, 3...). This means SWA averages over untrained early checkpoints,  
destroying any learned features.

**Evidence:**
```python
# SWA update — official applies SWA after every best model save
if use_swa and val["eer"] <= best_eer:
    optimizer.update_swa()
```

The comment itself says "official applies SWA after every best model save" — but the  
official paper does NOT do this. The official code uses a fixed start epoch (75) and  
fixed frequency (1), not "whenever EER improves".

## 🟠 HIGH RISK — Insufficient/Wrong Training Data

**File:** [`training/aasist/dataset.py` L28–L32](file:///c:/Users/HP/Desktop/deepfake(complete)/training/aasist/dataset.py#L28-L32)

```python
def scan_wavs(directory):
    """Return sorted list of .wav paths in directory."""
    ...
    return sorted(glob.glob(os.path.join(directory, "*.wav")))
```

**Problems identified:**
1. **Only `.wav` is scanned** — `.flac` files are ignored (the `src/` version scans both,  
   the `training/` version only scans `.wav`). If your data contains `.flac` files, they  
   are silently skipped, potentially halving your dataset.
2. **No minimum size check** — corrupted, empty, or near-silent files are loaded without  
   validation. A 0-byte file raises a `ValueError` in `load_wav` but only shows as a  
   DataLoader error, not a meaningful dataset count.
3. **Unknown actual dataset size** — without running the script we can't confirm how many  
   real vs fake files exist. If `data/real/` has only a handful of files, the model  
   sees the same audio repeatedly and memorizes rather than generalizes.

## 🟠 HIGH RISK — Scheduler Steps Per SWA Interaction

**File:** [`src/deepguard/aasist/train.py` L380](file:///c:/Users/HP/Desktop/deepfake(complete)/src/deepguard/aasist/train.py#L380)

```python
freq_aug=args.freq_aug, epoch=epoch, total_epochs=args.epochs,
verbose=args.verbose, scheduler=scheduler if not use_swa else None,
```

When SWA is enabled, **the cosine scheduler is passed as `None`** → learning rate never  
decays. The model trains with a constant LR of `1e-4` for all 100 epochs. Without LR  
decay, the model oscillates around a sub-optimal loss minimum rather than converging.

## 🟡 MODERATE — Dataset Split Uses Global Shuffle, No Stratification

**File:** [`training/aasist/dataset.py` L101–L103](file:///c:/Users/HP/Desktop/deepfake(complete)/training/aasist/dataset.py#L101-L103)

```python
combined = [(p, 0) for p in real_paths] + [(p, 1) for p in fake_paths]
rng = random.Random(seed)
rng.shuffle(combined)
```

**What happens:**  
A plain shuffle with no stratification means a small dataset (e.g., 50 real + 50 fake)  
could land all real files in train and all fake in test, or vice versa, due to the  
random seed. The val/test sets may contain **only one class**, which causes  
`compute_eer` to return the default `0.5`:

```python
if len(labels) < 2 or len(np.unique(labels)) < 2:
    return 0.5, 0.5   # ← this is your EER if split has one class!
```

## 🟡 MODERATE — Cosine Scheduler T_max Miscalculated With SWA

**File:** [`training/aasist/train.py` L230–L233](file:///c:/Users/HP/Desktop/deepfake(complete)/training/aasist/train.py#L230-L233)

```python
steps_per_epoch = len(train_loader)
total_steps = args.epochs * steps_per_epoch
scheduler = torch.optim.lr_scheduler.CosineAnnealingLR(
    optimizer, T_max=total_steps, eta_min=TRAIN["lr_min"],
)
```

The scheduler is built **before** SWA wraps the optimizer. When SWA wraps  
the optimizer, the scheduler's `optimizer` reference becomes stale. This means  
the scheduler steps have no effect on the actual learning rate being used.

## 🟡 MODERATE — `Residual_block.forward` Bug (Identity vs BN Input)

**File:** [`src/deepguard/aasist/model/aasist.py` L138](file:///c:/Users/HP/Desktop/deepfake(complete)/src/deepguard/aasist/model/aasist.py#L138)

```python
def forward(self, x):
    identity = x
    if not self.first:
        out = self.bn1(x)
        out = self.selu(out)
    else:
        out = x
    out = self.conv1(x)  # official: always takes raw x, not out
```

`conv1` receives `x` (raw input) even after BN+SELU is computed into `out`.  
The comment says "official: always takes raw x" — however this means the BN  
computation for non-first blocks is **completely wasted** (the output `out` of  
BN+SELU is discarded). This reduces the encoder's representational depth and  
makes gradient flow less stable.

## 🟡 MODERATE — `drop_way` Applied With `inplace=True` on Shared Tensors

**File:** [`src/deepguard/aasist/model/aasist.py` L362–L363](file:///c:/Users/HP/Desktop/deepfake(complete)/src/deepguard/aasist/model/aasist.py#L362-L363)

```python
self.drop = nn.Dropout(0.5, inplace=True)
self.drop_way = nn.Dropout(0.2, inplace=True)
```

`inplace=True` on dropout can corrupt tensors that are **referenced multiple places  
in the graph** (e.g., `out_T1 = out_T1 + out_T_aug` then `self.drop_way(out_T1)`).  
This can cause gradient NaN/inf on certain PyTorch versions, leading to training  
instability and high EER.

## 🟢 LOW — `WeightedRandomSampler` Only Applied for HF Datasets

**File:** [`src/deepguard/aasist/train.py` L265–L285](file:///c:/Users/HP/Desktop/deepfake(complete)/src/deepguard/aasist/train.py#L265-L285)

`WeightedRandomSampler` is only used when training on HuggingFace datasets with  
a `key` column. For local folder datasets, plain `shuffle=True` is used. If your  
local data is imbalanced (e.g., 10 real + 200 fake), every batch is heavily  
skewed toward fake, and the model learns to always predict fake → high FPR → high EER.

## Recommended Fix Order

### Step 1 — Verify the Master Node Bug is Fixed
Check if your checkpoint was trained **before or after** Bug #1 was fixed  
(the `.expand().clone()` call at line 442–443 of `aasist.py`). If before → **retrain**.

### Step 2 — Unify the Two Training Scripts
There should be **one** `train.py` and **one** `config.py`. The duplication in  
`src/deepguard/aasist/train.py` vs `training/aasist/train.py` causes configuration  
drift. Pick one, delete the other, and standardize.

### Step 3 — Fix Class Weights
For your local dataset (likely balanced `data/real` + `data/fake`), the correct  
class weights are `[1.0, 1.0]`. Only use `[0.9, 0.1]` or similar if you have  
confirmed a 9:1 fake:real imbalance.

### Step 4 — Fix SWA Start Epoch
Change `swa_start` to 75 (for 100-epoch training) or disable SWA entirely for  
initial debugging. SWA should only be enabled once the model is already converging  
well (EER < 20%).

### Step 5 — Add `.flac` to Local Scanner
```python
# training/aasist/dataset.py line 32
return sorted(
    glob.glob(os.path.join(directory, "*.wav")) +
    glob.glob(os.path.join(directory, "*.flac"))
)
```

### Step 6 — Add Stratified Split
Replace the plain shuffle split with `sklearn.model_selection.train_test_split`  
with `stratify=labels` to ensure both classes appear in every split.

### Step 7 — Monitor P(fake) std During Training
The diagnostic already added in `src/deepguard/aasist/train.py` prints  
`P(fake) std`. If it stays near 0.0 after epoch 1, you have representational  
collapse (Bug #1 or weight inversion). Stop training immediately and fix the root cause.
